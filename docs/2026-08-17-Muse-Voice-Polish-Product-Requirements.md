# Muse 语音输入三档模式产品需求

状态（2026-09-12）：三档目标已确认；轻度润色已由用户实录验收通过，标准润色正在接入校对与结构整理两步方案。整体三档版本尚未验收。
首次确认：2026-08-12
三档目标确认：2026-09-10

本文件是当前版本语音输入模式的产品目标、行为边界和质量验收依据；开发进度记录在 [REPAIR_PLAN L15](../REPAIR_PLAN.md)，工程方案记录在[架构方案](2026-08-17-Muse-Voice-Polish-Architecture-Reset.md)。需求确认不代表功能已经实现或通过验收。

## 1. 产品目标

Muse 语音输入提供用户可选择的三档模式：**直出、轻度润色、标准润色**。

直出沿用现有不润色行为；轻度润色兼顾速度与输入准确性，快速修正小瑕疵；标准润色负责内容结构与表达质量，同时保证错词纠正和原意准确。

两档润色都必须保留用户最终意图、事实和个人口吻，让输出适合直接发送、粘贴或继续编辑。修改幅度由所选模式和实际需要决定。

## 2. 三档模式及行为边界

| 模式 | 用户目的 | 允许的处理 | 主要验收重点 |
|---|---|---|---|
| 直出 | 直接取得识别文字 | 保持现有不润色流程，不新增 LLM 润色调用 | 与现有直出基线一致，无额外润色等待或改写 |
| 轻度润色 | 快速、准确地修正小问题 | 去掉非自愿口吃和机械重复，修正明确口误、有证据的错词及必要标点、断句 | 速度、准确性、最小必要修改，保留原句顺序和表达方式 |
| 标准润色 | 得到准确、结构清楚、表达自然的内容 | 在纠错基础上梳理逻辑、调整内容顺序、合并冗余、自然分段，按真实关系组织列表 | 信息完整、逻辑清楚、结构得当、错词准确、保留个人口吻 |

- 用户选择必须真实决定处理范围。轻度润色不能因输入变长或复杂而自动变成标准润色；内部策略可以调整，但必须遵守当前模式的边界。
- 轻度润色不承担整体重写、话题重排或自动列提纲。对无法确认的错词和含义保留原表达，不能为求通顺猜测事实。
- 轻度润色保留“帮我整理成 Prompt”“给客户回一下”等任务表达、受众和禁令，只纠正其中的局部问题；不能把这段请求当作 Muse 要执行的代写任务，改成最终客户回复或最终 Prompt。这是“去掉口误、修正错词”的范围约束，不以历史单模式代写要求扩大轻度职责。
- 标准润色按内容需要整理结构；自然短句可以保持不变，不为体现模式差异强行扩写、加标题或列点。
- 界面名称、实际调用路径、输出结果、历史状态与测试报告必须对应同一模式。
- 新模式与既有 `fast/balanced/quality` 或 Fast、Structured、Deep 等标识的关系，须在核对现有实现后制定兼容方案，不能仅凭名称直接映射。默认选择也须在实现方案中明确。
- 本目标定义语音输入的三档行为；现有翻译、Prompt 优化等其他处理功能的去留不在本次需求变更范围内。

## 3. 两档润色的共同准确性要求

### 3.1 理解用户最后真正想表达什么

- 识别即时或延迟改口、推翻、补充、放弃的半句话和顺序调整。
- 普通口误只保留最终有效版本，删除“我说错了”“不对”“改成”等修改过程。
- 公开更正、勘误或致歉通知例外：旧值和正确值都属于正文事实，必须完整保留。

### 3.2 按所选模式整理口语

- 轻度润色清理明确的口吃、机械重复和口误，只修改影响准确性与阅读的局部字词、标点和句界。
- 标准润色进一步处理同义冗余、断裂和乱序，重建句界与语义关系；多主题内容自然分段，真实步骤或并列事项可列点，没有列表关系时不得强行列点。
- 聊天仍像聊天，工作消息仍像工作消息，AI Prompt 仍然是待执行的 Prompt。

### 3.3 保留用户本人

- 保留最终事实、数字、日期、时间、金额、版本、路径、命令、专名、参与方、数量和独立动作。
- 原文未说明的币种、单位、理由或关系不能自行补充；整理结构也不能删掉仍有效的原因、要求、限制和待确认状态。
- 保留用户态度、表达力度、语气和个人声音。
- 不把用户改成客服腔、报告腔、营销腔或 AI 腔。
- 保留有意强调的原意和态度、节奏及并列关系；不要求重复次数原样保留。用户于2026-09-11明确确认，“千万千万”合并为“千万”属于可接受的轻度润色，不计为问题；明确口误未清理仍属于问题。

## 4. 长短文本要求

本节的润色要求分别按轻度与标准的行为边界判断；直出以现有不润色行为为基线。

### 4.1 短文本

- 只做必要修改，不扩写、不拔高、不补背景。
- 已经自然、准确、可直接发送的短句可以保持不变；“必须发生文字变化”不是成功标准。
- 问句、否定、情绪和语气不得被改掉含义；重复合并按实际表达效果判断，不因重复次数减少直接判失败。

### 4.2 长文本

- 真实质量验收输入上限为 1,000 字，长文重点覆盖 700～1,000 字。这是本轮测试范围；更长文本不再作为修复或验收用例。
- 不得压缩成摘要，不得遗漏独立事实、要求、限制或行动项。
- 不得因输出截断、超时、校验误判或内部路线选择而静默退回原文。
- 轻度润色保持原有叙述顺序，只修局部问题；标准润色保持全文完整，并按主题、步骤和并列关系建立可读结构。
- 当前版本不把超过 1,000 字的压力测试或超长分片改造列为开发、验收前置条件；已有历史测试数据保留用于追溯。
- 安全回退仍可作为最后防线，但回退原文只能算安全机制成功，不能算润色质量通过。

## 5. 上下文纠错要求

- 可使用已确认术语，以及用户已授权的安全输入框附近文字、选中文本和同一应用近期 Muse 输入。
- 上下文只用于纠正有证据的错别字、专名、指代和表达，不得把上下文中的无关事实带入正文。
- 多个上下文证据冲突、证据不足或控件不安全时，保留原表达，不猜人名、品牌、项目名或事实。
- 密码框、网页或自绘输入区、未知控件和读取失败时不得读取正文。

## 6. 明确不做什么

- 不回答语音中的问题。
- 不执行语音中的命令或 AI Prompt。
- 必须区分“这次如何编辑”的要求与“交付给收件人或未来 AI 执行”的正文任务；前者仅在所选模式允许的范围内应用，后者作为正文保留，不能误删或混入。
- 轻度不因出现代写或整理要求而执行任务、改变交付角色。标准在缺少当前收件人上下文时是否默认代写最终正文，仍需单独明确；三档目标的确认不等于确认这个默认。
- 不把长内容擅自总结或缩写。
- 不新增原文没有的理由、承诺、人物、例子、结论、标题、金句或营销话术。
- 不用漂亮措辞掩盖事实、意图、语气或信息缺失。

## 7. 质量测试维度

同一批输入必须分别测试直出、轻度润色、标准润色，并为每档规定允许修改和应保留的内容。不能用标准润色的结构要求判定轻度不合格，也不能要求直出修复 ASR 错误。测试集同时覆盖以下维度，不能只靠同一模板换尾句：

1. 文本长度：极短 1～15 字、短 16～80 字、中 81～300 字、长 301～1,000 字，其中须有 700～1,000 字自然长文。
2. 写作场景：私人聊天、工作沟通、邮件、文档、笔记、AI Prompt、社交内容、技术表达、客服沟通。
3. 口述噪声：口误、口吃、字词重复、同义反复、半句话、乱序、错标点、错断句、词内误空格。
4. 上下文：安全附近文字、选中文本、近期 Muse 输入、冲突上下文、不安全或无授权上下文。
5. 事实安全：数字、日期、金额、版本、专名、路径、命令、名单和独立约束。
6. 模式边界：轻度保留叙述顺序并控制修改范围；标准按真实关系分段、列点和组织行动项；直出保持基线。
7. 不过度改写：自然短句保持简洁，保留原意、态度与表达效果，允许不影响这些内容的重复合并。
8. 失败恢复：截断、超时、模型失败、校验拒绝和回退原因可审计。
9. 性能与稳定性：各模式的调用次数、重试次数、耗时 P50/P95、失败率、连续输入及切换模式后的实际行为。

耗时分别记录“停止说话至文字可用”和“ASR 最终结果就绪至文字可用”，区分识别等待与润色开销，并记录模型、服务端点、文本长度及测试环境。轻度必须以减少额外等待为设计重点；具体时间预算先通过基线测量制定，不能把尚未测量的秒数写成已达成指标。

## 8. 验收标准

- 直出须与现有不润色基线一致，不引入润色调用；既有识别错误单独记录，不算润色纠错失败。
- 轻度润色以快速、准确、最小修改为首要目标；标准润色以准确、结构清楚和自然表达为首要目标。两档分别统计 `direct_send`：用户无需修改就愿意直接发送、粘贴或保存。
- 两档润色的关键事实、最终意图和无来源实体错误数必须为 0，不能通过降低准确性换取速度或结构评分。
- 每个长度桶、上下文类型和核心输入因素都必须达到测试集明示覆盖门槛。
- 当前从历史母集原样筛选不超过 1,000 字的输入，并补足自然长文；记录排除项、覆盖量和独立输入哈希，按基准与脏输入分别评分。历史 130 条规模不再是本轮真实验收门槛，原母集和历史报告保留用于追溯。
- 两档润色各自对基准输入与脏输入分别满足现有质量门槛：`direct_send ≥ 85%`，`direct_send + minor_edit ≥ 95%`；不得合并两档成绩掩盖任一档失败。
- 长文本和上下文纠错专项不得出现 `major_edit`、`unusable`、截断或静默回退。
- 短文本专项不得出现多余扩写或改变原意、态度、否定边界；“千万千万→千万”等用户认可的重复合并不计为失败。
- 轻度须通过编辑范围与速度专项，标准须通过结构与完整性专项；速度预算须有测量依据，并在最终验收前明确记录。
- 单元测试和模拟响应只证明工程边界；真实成稿质量必须用真实 Provider 输出评审。
- 最终验收必须由未参与实现的独立 Agent 执行。独立 Agent 未明确通过时，不得标记完成、提交发布结论或部署新版。

## 9. 工程研究范围

- 从三档目标重新检查界面选择、配置兼容、ASR 后处理入口、润色管线、提示词、模型调用、校验、失败恢复和输出注入，不把修复限定为修改提示词或更换模型。
- 现有 Intent Ledger、Writer、Reviewer 和局部修复等组件可按证据复用、简化或调整；三档无须共享同一套调用流程。
- 使用相同输入做受控对比，分别判断原始识别、生成、复核、修复和最终输出的问题；已有方案、模型或单次实验结果不预设为最终答案。
- 先形成符合各档目标的可测方案，再以真实质量与速度证据决定实现；最终方案须简单、可维护。

## 10. 验收责任

- 实现 Agent：编写需求、实现、测试集和确定性测试，不得自行给出最终质量通过结论。
- 验收 Agent：独立运行测试、检查覆盖和结果，明确列出通过项、失败项和阻断项。
- 验收 Agent 必须亲自从冻结提交打包候选应用，并由硬验收程序直接启动候选内置 Runner 取得原始 Provider 报告；不得接受预先生成或由实现 Agent 提供的 JSON。报告必须使用一次性运行标识，并绑定本次进程、运行时间、候选应用内写入的提交、实际二进制哈希、完整 Provider Endpoint、数据集哈希、原始分段和上下文夹具；每条结果必须记录用户所选模式、实际路径、真实调用次数与耗时证据。直出的润色调用次数应为 0，不伪造 Provider 回执。
- Runner 验证正式语音润色核心链路，但固定使用空个人词库、空片段和空风格画像；它不能替代安装版真实麦克风、ASR、个人化数据与文字注入冒烟。
- 只有验收 Agent 明确给出“通过”，且构建、全量测试与安装版验证同时通过，修复台账才可销账。
