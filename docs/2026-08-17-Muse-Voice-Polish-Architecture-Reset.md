## 2. 第一性原则

### 2.1 所选模式决定交付物

直出交付现有不润色流程的识别文字。轻度只做必要的局部纠错，保留叙述顺序与表达方式；标准可调整顺序、合并冗余、自然分段或列点。复杂度可以影响当前模式内部的处理，但不能自动改变用户所选模式。

两档润色均须区分有效正文、改口过程和当前编辑要求，保留收件人、最终事实、独立约束、待确认状态、态度和有意重复。原始输入必须保留，不能用经过删改的中间稿替代最终复核的来源。

### 2.2 每个新增判断都必须有来源证据

模型不得根据常识补写用户没有说出的理由、承诺、结论、人物、单位、币种或数据。发生实质修改时，必须能对照原文和已授权上下文解释依据；采用意图清单的路径中，每个项目都须引用原始片段或字符范围。

### 2.3 安全检查只裁决能够确定证明的错误

本地程序可以确定检查空输出、截断、明确数字和代码标识损坏、已绑定旧值残留、上下文秘密泄漏等问题。自然度、同义改写和开放式语义关系不能由固定词表或正则表达式直接判死刑。

### 2.4 一个局部失败不能拖累整篇

修复应限定在已定位的问题及必要的相邻上下文，避免反复重写已正确内容。修复之后必须核对实际最终稿；不能以首稿或中间清单通过代替最终输出通过。

### 2.5 失败必须可见

未通过硬检查或语义复核的候选不得冒充成功成稿，也不得静默退回原文。产品必须保留原转写，并明确提供“重新润色”“使用原转写”两个出口；失败状态不属于普通设置复杂度。

## 3. 当前编辑协议与保留的旧组件契约

当前候选的 `VoicePolishEditingPrompts` 独立版本化，v4 生成及每一轮复核请求包含所选 `mode`、完整 `canonical_text`、保留 ASR 边界的 `source_segments:[{id,text}]`、写作场景与用户表达偏好。`authorized_context` 只包含本地 `EntityResolver` 已验证且应用的词语映射，不发送整段附近文字或近期输入；标准复核还包含实际 `draft_text` 和程序计算的 `changes`。`source_segments` 直接取输入 envelope 的 canonical 分段，保留原 ID、顺序和片段文字；本地 EntityResolver 映射后的完整正文仍由 `canonical_text` 独立提供。分段仅是来源边界，不能把 ASR 切块一律当作逻辑段落，也不能用它撤回已验证词语纠正。真实来源审计逐阶段绑定两者，不能用中间摘要替换来源。

内置编辑协议使用 `structuredTask` 请求，保留自身完整输入边界；不再叠加自定义处理模式的通用封装。当前编辑要求只能影响本档允许的文字转换，正文中的问答、命令与未来任务不能被执行。这项边界简化是否改善真实输出须经新候选实测，不能仅凭措辞判断因果。

轻度返回 `{"edits":[{"before":"唯一连续原文片段","after":"局部替换结果","kind":"编辑类型"}]}`；标准首稿为纯文本。两档v5复核返回 `delivery`、`edits`、`editor_spans`；交付类型为 `direct_reply / ai_prompt / delegated_task / other_or_uncertain`。成稿默认由说话人署名，原文没有明示中间执行者时不能凭空增设同事代写。`editor_spans` 只列当前编辑短语，逐字唯一地定位完整来源，不复制全部正文任务，不带判断解释；混合句中的预算、原因和条件仍属于正文。当前编辑要求留在实际稿时必须提供合法局部补丁，否则失败；引用与交付标签均不授予删除权限。程序继续验证定位、范围、类型和已有事实边界，且区分复核协议错误与实际编辑权限错误。交付类型和引文语义仍由模型判断，真实准确性必须独立验收。详见第4、5节。

轻度的跨段明确改口复用 `correction.evidence`：证据必须是完整来源中的连续原句（≤192字），包含明确改口标志；仍只在原位置改变一个短字词块（删除≤32字、插入≤8字），插入内容须逐字来自证据，单项原文锚点≤96字。管线显式开启这项权限且必须核对实际稿后才能交付，来源匹配本身不证明对象归属正确。保留原有段落和其余文字顺序，不通过扩大全文改写权限实现轻度纠错。

以下第 3.1、3.2 节记录保留的旧 Ledger 路由契约，供兼容与工程回归使用，不是当前轻度、标准模式发送给模型的协议。

- `source_spans` 必须能在 canonical source 中定位；
- `replace` 必须同时指明被替换对象和最终对象；

- `dictated_symbol_mappings` 只处理原文明确口述的固定 ASCII 符号；路径/文件名做符号直换，命令参数可额外恢复参数前的必要空格，非符号字符必须逐字不变；
- 映射字段不能代替正文 unit；错误放入技术映射的恒等项或可确定的口述符号项由本地清洗器删除或迁移，不为此再调用模型；
- `modality` 必须区分“不会发生”“不要承诺发生”“已经承诺”“尚未确认”“可能发生”和“建议执行”；
- 故障现象与后续建议必须拆开；`advice/recommended` 不能被 Writer 升级为确定因果或保证结果；
- 收件人和转达动作必须成为一等信息，不能依赖普通名词保留检查。
- Planner 已从原文提取出的收件人必须带可回溯 `surface_tokens`；最终成稿至少命中一个，缺失时只修收件人，不重写全文。

复核器不重写全文，只输出可定位的问题：

```json
{

  "issues": [
    {
      "unit_id": "u1",
      "type": "missing|wrong_relation|wrong_modality|obsolete_retained|invented|context_leak|style_shift",

      "repair_instruction": "恢复团队这一接收对象"

```

使用此契约的复核器必须核对原文与实际成稿的对应关系，检查遗漏、改意和无来源新增。清单项目有来源、单元 ID 被覆盖，都不能独自证明原文的全部有效信息已保留。

## 4. 当前候选的分模式处理路线

### 4.1 共用入口

1. 接收并保留 ASR 原始分段、canonical text、用户所选模式、写作场景和已授权上下文；
2. 首先按模式分流，直出保持既有路径；润色路径中的本地标准化仅限有证据的术语、符号与字符处理；
3. 在当前模式允许的编辑范围内判断处理需要，记录实际路径、调用次数与耗时。

产品档位由稳定输入模式 ID 推导。标准沿用原 `formalWriting` ID，新设轻度 ID；旧配置加载时只在内存补全系统模式，保留用户自定义名称、附加要求和快捷键。轻度默认 Option+4，已有绑定冲突时不覆盖；标准继续使用既有绑定。设置页分别保存两档附加要求，并按所选档位试跑和展示性能。

录音中允许切换结束时使用的模式；停止后冻结模式，用户重试保持本次档位，迟到的模式切换不能给已经处理的结果改名。新历史记录保存实际模式名，旧记录不根据路由猜测档位。 正式会话另记录首次自动结果、用户重试、实际局部修复和最终出口；质量Runner同时透传实际修复尝试次数，未进入客户端的预算预检失败不算模型请求；用户选择原文或重试成功不能覆盖首次失败。停止至可用、ASR终稿就绪至可用分别记录净处理耗时，扣除用户决策等待并明确注明。旧样本缺少的字段保持未知，不混入新口径统计。

文本长度、改口、数字、收件人和上下文等信号用于测试覆盖与定位问题，不能自动改变用户所选档位。

### 4.2 直出

沿用现有不润色流程，不新增 LLM 润色调用。验证模式选择、输出与原有基线一致，并检查切换模式后不会残留上一档的处理任务或状态。

### 4.3 轻度润色

当前候选路线为“完整原文 → 一次模型局部 edits → 本地核验实际变化 → 按原文风险或实际语义修改决定是否复核”。机械变换的完整性由程序证明，允许组合有边界的短停顿声删除、确定性技术符号恢复和必要标点，不依赖模型填的kind决定免审；叠字是否口吃涉及人名和实词，删改必须语义复核；技术词边界按实际原文检查，不能通过窄锚点绕过；整份变化无法证明时仍按受限类型校验，不能部分落稿。原文出现编辑或改口风险时，首轮空edits也须复核。轻度复核只允许一次局部修复，仍使用轻度权限，再确认实际修后稿；正常机械输入一次调用，需核对时两次，有修复时最多三次，共用20秒总预算。额外等待与效果必须用新候选实测。

- 只处理明确口误、口吃、机械重复、有证据的错词和必要标点、断句，保留原句顺序。
- 已自然准确的输入允许不变，不为了展示润色而重写。
- 轻度核对使用完整原文、实际局部稿、程序计算的真实修改、交付类型和当前编辑短引文；发现漏改时允许一次轻度局部修复，不能使用content重写。无标点短编辑前缀可以带未变正文后缀定位，只删一个连续短片段（≤32字），不能移动、插入或清空全文，必须核对实际结果。非空终审、补丁不合法、超时或事实检查失败时显示失败出口；用户主动重试另计。
- 对证据不足的词义保留原表达。已确认存在关键错误的候选须显式失败，不能假装纠错成功。

### 4.4 标准润色

当前候选路线为“完整原文直接生成纯文本首稿 → 冷复核原文、实际首稿及程序计算差异”。复核未提出修改时通常共两次调用；提出有来源的局部修正后，由程序检查并应用，再发起一次针对实际修后稿的冷确认，自动流程最多三次调用。确认仍要求修改、补丁无效或事实检查失败时不交付候选稿。该路线尚未经过本轮真实模型质量与速度验收。

- 按真实主题、步骤和并列关系组织内容，整理乱序与冗余，保留原因、约束、最终改口和个人语气。
- 标准始终对实际首稿发起独立复核；原文未改或字面相近也不能替代对否定、单位和语义的核对。发现问题后只允许局部修正，不能反复重写正确部分。
- 自然短句可以保持不变；700～1,000 字长文重点验证完整性与结构。
- 原始候选、每次复核、修复和最终输出分别留证，避免中间步骤把正确内容删掉而最终仍报成功。

超过 1,000 字的测试或超长分片改造不作为当前版本前置工作。各档仍须有明确的超时、截断和失败处理，不能静默回退并宣称润色成功。

### 4.5 本轮速度验收预算（待验证）

前三轮同13条诊断中，轻度P50为852～973ms、P95为1734～4089ms；标准P50为1522～1684ms、P95为3082～5089ms，包含失败样本。基于这组已测基线，在下一候选真实测试前制定本轮工程预算：轻度“ASR终稿就绪至输出”P50不超过2秒、P95不超过6秒；标准分别不超过3秒、8秒。保留每条耗时，并分别报告模式、基准/脏输入及长度桶，完整验收按各模式全组计算，质量门槛独立适用。预算留出必要语义核对与千字内长文的开销，尚未证明新流程达标。

这些数值只约束当前合成文本Runner能测量的润色开销；实际停止说话至可用的麦克风、ASR和输入注入耗时仍须另测。本节预算须与真实结果并列报告，不能因质量失败而省略失败样本，也不能在验收后悄悄调整门槛。


## 5. Writer 与 Reviewer 的职责隔离

当前标准模式中，Writer 根据完整 canonical 原文生成草稿；Reviewer 使用独立请求上下文，同时读取完整原文、已验证且应用的词语映射、实际候选和程序计算的差异，不接受 Writer 的自我评价或中间清单替代证据。

同一 Provider 可以承担两个角色，但使用隔离调用。检查必须同时回答“原文的有效信息在成稿何处”和“成稿的信息来自何处”，不能仅确认引用真实或清单项已覆盖。

轻度在原文风险或实际语义变化触发时执行自己的核对，修复仍严格限定在轻度局部权限，并须确认修后实际稿；标准的合法结构调整不能被误判为改意。同模型隔离请求不保证消除共同盲点，交付标签和引用存在也不能证明修正符合原意；最终独立质量验收始终需要。

## 6. 本地硬门禁的新边界

### 6.1 当前已接入的程序检查与待验证边界

当前编辑路径检查输出为空、异常长度、危险字符、来源事实与单位，以及局部补丁定位唯一性、修改范围、类型和重叠等确定性条件。自然语言中的数字、时间和单位须基于完整原文核对；口述符号投影只能作为技术字符的额外匹配来源，不能把“三点”或“重点”中的“点”先改掉再判断事实。

独立审查后的候选进一步收窄相邻重复处理，并补充技术口述符号、明确少字补字、短的当前编辑指令和命令配对反引号检查；这些补充由独立反例复核和工程回归验证。轻度的紧邻时间改口仅在两个时间事实之间只有明确改口词时承接最近日期与时段；中间有另一个事项则不推断。标准稿中其他日期省略承接必须进入语义复核，允许继续复核不代表程序已证明时间关系正确。

以下是产品要求保护的边界清单，不表示每项都已由新候选的本地程序完整证明。上下文仅发送已验证且应用的词语映射，也不保证开放式含义和遗漏已被解决，仍需复核及真实输出验收：

- 空输出、明显截断、Provider 长度终止；
- 受保护数字、金额、日期、时间、版本、路径、命令、邮箱和 URL 的确定性损坏；
- 已经通过对象绑定证明的旧值残留或最终值缺失；
- 明确授权映射未执行、映射被用户否认却仍执行；
- 上下文中的无关隐私或 trap 进入成稿；
- 完全重复的整篇输出、缺失章节、内部片段未完成；
- 成稿回答或执行了 AI Prompt，而不是交付 Prompt 本身。

### 6.2 降为诊断或交给 Reviewer

- 固定短语是否逐字出现；
- 同义表达是否与参考答案字面一致；
- 开放式负责人、动作、时间关系的正则推断；
- 自然段数量、标题措辞和非明确列表的排版偏好；
- 是否“改得足够多”；
- 个人口吻和自然度。

现有 Validator 中的确定性字符、事实和安全组件按实际接入情况复用；不得把旧管线的全部校验能力写成新候选已经覆盖。依赖冻结样本措辞、开放式中文语义或大量词表推断的部分不得继续作为整篇回退条件。

## 7. 模型能力契约与受控对比

分别验证两档润色在实际配置模型上的能力：

- 能稳定遵循当前档位协议：轻度输出局部 edits，标准生成纯成稿，两档复核输出delivery、editor_spans和edits；不回答或执行输入；
- 能保留长文本独立约束；
- 能区分撤回、最终值、否定、未确认和不承诺；
- 能遵循来源证据，不补写事实；
- 轻度能遵守最小修改范围与速度预算，标准能在保留信息的前提下整理结构；
- 采用结构化路径时，能按该路径需要的 JSON schema 输出。

以同一批输入和场景建立三档各自的输出契约。在固定模型配置下先比较提示与工程路径，分别记录：

1. 直出基线，以及两档润色各自的原始生成结果；
2. 复核、修复、本地校验各阶段输入与输出；
3. 用户实际收到的文字、失败状态和改动范围；
4. 模式、实际模型与端点、调用与重试次数、耗时分位数、截断和失败原因。

评分由未参与实现的独立 Agent 按各档契约执行。原始成稿合格而最终失败时，须定位复核、修复或校验中的具体原因；多个模型在同一处失败不足以单独证明根因。当前研究不以加测 Pro 或更高价模型为前置条件，不隐式替换用户日常模型。

## 8. 核心样本与验收分层

### 8.1 核心产品集

复用既有真实核心样本，并补足能区分三档行为的用例。每条按模式规定契约，不规定唯一成稿：

- 最终意图；
- 必须保留；
- 必须删除或作废；
- 禁止新增；
- 可以接受的同义和结构变化；
- 直出应保持的基线、轻度的局部编辑范围、标准需要的结构；
- `major_error` 与 `unusable` 的明确边界。

核心集至少覆盖极短消息、有意重复、口吃、即时与远距离改口、收件人、否定和承诺、上下文纠错、AI Prompt、代码、客服披露、自然叙述、真实清单。全部输入不超过 1,000 字，700～1,000 字为长文重点。原超长失败若有适用于日常长度的核心问题，另建完整的新样本并使用新 ID，不能截断旧样本冒充相同输入。

### 8.2 工程测试

工程测试验证模式选择、配置兼容、路由与调用预算、来源绑定、问题定位、局部修复权限、失败状态及上下文安全。模拟响应不能证明真实润色质量或速度达标。

### 8.3 完整验收子集

历史母集、报告和原始回执保持不变；当前原样筛选不超过 1,000 字的输入，补足自然长文，并新建按模式评分的契约与报告，独立冻结输入哈希和覆盖统计。能够确定证明的检查保持硬门禁；开放式关系和自然度由独立 Agent 结合各档契约评分。

轻度与标准各自按基准、脏输入和长度桶报告质量，不能把两档混算。验收须记录从停止说话、从 ASR 最终结果就绪到文字可用的两段耗时及 P50/P95；先测量基线，再明确各档速度预算，不能把未测量的目标标为通过。签名候选 Runner 的合成文本测试只测文本准备后的处理耗时，不包含真实麦克风、ASR 与文字注入；安装版端到端耗时须另行验证。性能页的“无修复完成”按自动会话统计，标准正常的生成与复核不算修复。

## 9. 实施顺序和停止线

1. 以三档产品需求为准，保留已有失败样本与实验来源；
2. 在候选代码中接入界面、存储兼容和模式处理路径，先完成工程边界验证；
3. 完成同输入的三档验收契约，测量当前质量与耗时基线；
4. 在隔离候选中比较轻度、标准的处理方案，定位生成、复核、修复与校验各自的问题；
5. 候选可先集成界面和正式调用入口以验证完整链路；这不代表发布。两档核心集须分别达到编辑范围、关键事实与最终意图零错误、结构与速度目标；
6. 完成相关工程测试、全量测试、Debug/Release 构建和 1,000 字以内的分模式验收子集；
7. 最终由未参与实现的独立 Agent 从冻结提交打包、跑真实 Provider 并逐条评分；
8. 独立 Agent 未明确通过时，L15 保持进行中，不安装候选。

禁止事项：

- 不为单个测试句继续添加生产字面特判；
- 不通过削弱事实安全门禁换取通过率；
- 不把参考答案当作唯一合法表达；
- 核心回归未通过前不扩大到完整验收子集；
- 不由实现 Agent 自行宣布质量通过。

## 10. 历史受控实验记录

以下保留当时输入、模型、代码与结果，供定位问题和比较方案使用。后续开发目标与测试范围以第 1～9 节及产品需求文档为准，历史实验不能替代三档验收。

### 10.1 实验边界

- 实验完全位于 Muse 正式 Pipeline 之外，没有改动、打包或安装生产应用；
- 25 条核心集不向模型提供参考答案、`semantic_contract` 或自动评分字段；
- 凭证只通过标准输入进入进程，报告与模型输入中不保存 API Key；
- 当前模型为 `deepseek-v4-flash`，更强对照为 `deepseek-v4-pro`；
- 候选隐藏模型名称后，由未参与实现的独立 Agent 评分。

证据目录：

- AI Prompt 定向对照：`build/voice-polish-architecture-targeted-span-v5/`
- 6K 长文最终定向对照：`build/voice-polish-architecture-6k-final-span-v6/`

### 10.2 已被证实有效的结构

1. `Intent Ledger → Writer → 冷 Reviewer → 局部 Repair → Confirm` 可以在失败时返回显式 `unavailable`，不再静默退回原文；
2. 6,179 字单 segment 长文可切成 14 个带范围和哈希的 source spans，并在 8～11 次有界调用内完成；
3. 全文改口投影和旧位置门禁已把“重试三次 → 最多两次”收口为：旧值为零、最终值只出现一次；
4. 高置信残缺尾句“还有日志那块呃后面那个”被删除，没有被擅自补成待确认事项；
5. AI Prompt 的任务层硬检查已删除“不要开始研究，只整理任务”等当前编辑指令，并阻止把“整理 Prompt”再次交给下游 AI。

### 10.3 模型不是单一强弱关系

独立盲评结果：

| 场景 | `deepseek-v4-flash` | `deepseek-v4-pro` |
|---|---|---|
| AI Prompt（约 1,000 字） | `unusable`，安全退出 | `direct_send` |
| 6K 单 segment 长文 | `minor_edit` | `major_error` |

这批历史样本只说明不同任务上的模型表现存在差异，不能据此决定全部输入统一换模。它曾留下以下待研究问题；是否继续研究须服从当前三档目标与千字内测试范围：

- AI Prompt 等任务层复杂输入是否稳定需要 Pro；
- 普通长文 Writer 是否由 Flash 更稳；
- Reviewer 是否应使用与 Writer 不同的模型，减少同模型盲点。

### 10.4 新发现的架构缺口

更强模型在 6K 长文中把：

> 独立 Agent 未明确通过时，不更新修复台账，也不覆盖安装。

错误写成：

> 只有独立 Agent 明确通过后，才更新修复台账，也不覆盖安装。

定位结果显示错误已经出现在局部 Intent Ledger，Writer 只是照写，Reviewer 又因为看到同一份错误 Ledger 而放行。根因不是措辞，而是 `final_meaning + modality` 无法表达条件、否定范围与多个共同后果。

下一版 Ledger 必须增加结构化条件规则，而不是继续增加中文正则：

```json
{
  "conditionals": [
    {
      "condition": {
        "subject": "独立 Agent",
        "predicate": "明确通过",
        "polarity": false,
        "source_spans": ["s006"]
      },
      "consequences": [
        {"action": "更新修复台账为完成", "polarity": false},
        {"action": "覆盖安装正式应用", "polarity": false}
      ]
    }
  ]
}
```

Reviewer 必须对照原始 source spans 独立重建这类高风险条件，不能只检查 Writer 是否遵守 Planner。上下文实体统一也仍有缺口：两个 6K 候选均混用 `Muse` 与“缪斯进程”；实验解析器选择不猜是安全的，但在进入生产前应复用经过正反例验证的确定性 EntityResolver。

### 10.5 约 1K 主场景验证

用户确认日常长文本一般约 1,000 字后，实验改用 1,028 字课程交接邮件验证 typed conditional Ledger。两种模型都完成 3 个高置信条件关系的结构化建模，且均在 `Planner → Writer → Reviewer` 三次调用内返回成稿，无 repair、无 fallback：

- 临时改口时只同步最新版本，并在标题标注日期；
- 无法按时完成时写明真实原因，只调整受影响部分，不默认整期延期；
- 素材可下载不等于可进入付费课程，版权依据仍须核对。

独立 Agent 在隐藏模型映射的情况下评分：`deepseek-v4-flash` 为 `minor_edit`，唯一问题是把“语气不用催”这类风格要求写进正文；`deepseek-v4-pro` 为 `direct_send`，把该要求自然落实为收件人可读的语气。没有候选出现事实、条件、改口或不承诺边界错误。

这说明 typed conditional 已解决本轮 1K 样本的主要语义风险，但 Ledger 还必须增加 `delivery_role`，把 `recipient_content`、`style_directive` 和 `editor_directive` 分开。风格与编辑要求只执行、不照抄；该结构完成小批量回归前，仍不进入生产。

### 10.6 首批核心回归与跨模型复核

在 6 条核心样本上进行双模型盲测后，发现同模型 Writer 与 Reviewer 会共享盲点：Flash 漏掉“团队”接收对象且自审放行；Pro 漏掉“原定周二录制已经取消”且自审放行。单纯交换 Reviewer 模型仍无法稳定抓住收件人遗漏，因此模型互审不能替代可证明的本地边界。

随后增加两项 typed 义务：

- `correction.rendering_policy = final_only | announce_change`：区分当前口误只留最终值，与旧安排已经对外、必须明确通知取消/变更；
- `audience.surface_tokens`：Planner 已从 source spans 识别出的收件人称谓，最终成稿至少命中一个，否则只修复收件人。

最终定向回归结果：

- 1,028 字交接邮件的两个模型候选均为 `direct_send`；周二取消、周三录制、三组条件关系、发布承诺和全部主要任务簇完整；
- 收件人样本的两个候选均不再出现重大遗漏，独立 Agent 仅判“团队，会议改到……”称呼略生硬，为 `minor_edit`；
- 本轮 `major_error = 0`、`unusable = 0`，且没有原文 fallback。

由此确定：确定性门禁只负责收件人、精确事实、上下文安全等可证明义务；中文称呼是否自然仍交给 Reviewer 与独立 Agent，不能为了消灭一个轻微措辞问题继续扩大本地中文规则。

### 10.7 建议语气、技术标识与模型边界

对“当前故障现象 + 建议下一步”的短文本增加 `advice/recommended` 后，两个模型都能保留现状并把“开启辅助功能”写成建议，没有再升级成“开启后一定恢复”。独立 Agent 对两个候选均判定为 `direct_send`。这证明建议与确定事实必须在 Ledger 中分开，不能只靠 Prompt 中一句“不要承诺”。

技术错误信息暴露了另一条第一性边界：ASR 将 `MainActor` 写成 `Main Actor` 后，原始声音已经丢失了技术标识的字符边界。没有代码上下文、已授权术语或其他权威证据时，模型只能猜。

两轮盲测出现了反转：

- 严格要求“每条映射只恢复一个技术标识”时，Flash 输出精确错误信息并获 `direct_send`，Pro 因无法给出合法映射而安全返回 `unavailable`；
- 临时允许模型用整句映射选择性删除空格后，Pro 获 `direct_send`，Flash 仍输出 `Main Actor`，被独立 Agent 判为 `major_error`。

因此不保留整句映射放宽。正式设计应按以下顺序恢复技术标识：已授权个人术语或选中上下文、产品内置且可审计的技术词典、单个标识的高置信空格删除；三者都没有证据时显式标记无法确认。模型可以提出候选，但不能单独成为技术 token 的事实来源。

这也回答了模型选择问题：模型会影响一次成稿率和安全退出率，但本轮同一用例已经出现模型间反转，不能把“换成 Pro”当作功能修复。决定产品是否可靠的是 typed Ledger、证据来源、独立 Reviewer 和显式失败；模型只是在该架构内影响成功概率。

实验工具同时增加了 Provider 请求的绝对墙钟超时。socket 持续收到分块数据但响应始终不结束时，也会在上限内写入失败审计，不再无限等待。

### 10.8 日常 1K 长文的模型分工证据

最后使用 1,003 字的真实 AI Prompt 场景做停止前检查。输入要求把一段研究口述直接整理成可执行 Prompt，同时保留来源边界、价格字段、三档长文本测试、上下文正负例、评分口径、引用规则、安全要求和反例检查，并使用安全选中标题把“北城研究”纠正为“北辰研究”。

结果：

- Pro 经一次定向修复后生成完整可执行 Prompt，12 类约束、项目名和安全边界均保留；没有开始执行研究，也没有泄漏选中上下文中的包装、日期或测试标记。独立 Agent 盲评为 `direct_send`；
- Flash 的首稿与修复稿仍残留“整理为 Prompt”的外层任务。Confirm Reviewer 拒绝后返回 `unavailable`，没有把错误候选或原转写冒充成功。独立 Agent 对空候选判为 `unusable`，与系统显式失败状态一致。

结合 1,028 字普通交接邮件中两个模型均可直接发送，这批历史实验中 Pro 在该复杂 AI Prompt 样本上更稳；该结果只适用于当时样本与配置，不代表三档产品的模型选择已经确定。当前依三档目标分别验证工程路径与模型表现，无法完成时须明确提示，不能静默回原文并宣称成功。

### 10.9 第二批核心关系回归

第二批先用 `chat-03`、`work-02`、`work-03`、`code-03`、`code-05` 检查承诺、负责人关系、延期状态、口述技术符号和不确定版本。首轮没有出现危险成稿，但暴露出三项 schema 缺口：已经作出的联系承诺没有 `promised`，建议动作可能自然建模为 `action/recommended`，中文口述的斜杠和短横线被错误塞进普通技术断词字段。

本轮没有为具体句子增加答案特判，而是做了三项通用改动：

1. `promised` 只保留原文已经作出的承诺，Writer 不得扩大承诺范围；
2. `recommended` 可以修饰 action、advice 或 style，但 advice 必须使用 recommended；
3. 口述符号使用独立 `dictated_symbol_mappings`。路径和文件名只做固定符号替换，命令行选项使用 `spoken_cli_symbols` 恢复参数前的必要空格，非符号字符必须逐字不变。

Planner 偶尔会把恒等命令或口述符号映射重复写进 `technical_token_mappings`。这类字段分类错误不需要再次调用模型：本地清洗器删除恒等项，把能够由固定变换确定证明的条目迁回口述符号字段；无法确定的映射仍然失败，不能猜测。

定向回归证据：

- `build/voice-polish-architecture-core-corrections-v20/`
- `build/voice-polish-architecture-core-relations-v21/`
- `build/voice-polish-architecture-schema-relations-v22/`
- `build/voice-polish-architecture-dictated-symbols-v24/`

独立 Agent 在看不到模型映射的情况下，对更新后的 10 条核心样本、每条两个候选给出：`direct_send = 16`、`minor_edit = 4`、`major_error = 0`、`unusable = 0`。其中 `code-03` 的两个候选都精确保留四步、`swift test`、`swift build -c release`、`scripts/package-app.sh`、codesign 检查和最后启动顺序。

4 个轻微问题集中在两个通用边界：公开改口成稿仍会残留已作废的“第二版”，未确认版本成稿仍会照抄“不要替我确定”这类幕后措辞且缺少自然的后续确认表达。下一批只处理 correction rendering 与 editor directive 的语义边界，不扩大到完整 130 条，也不据此接入生产。

### 10.10 完整核心集盲测与模型决策

25 条核心语义集完成双模型、隐藏模型名称的独立盲评，共产生 192 次真实 Provider 调用。解封模型映射后的结果为：

| 模型 | `direct_send` | `minor_edit` | `major_error` | `unusable` |
|---|---:|---:|---:|---:|
| `deepseek-v4-pro` | 23 | 1 | 1 | 0 |
| `deepseek-v4-flash` | 19 | 2 | 1 | 3 |

Pro 的一次成稿率为 92%，`direct_send + minor_edit` 为 96%；Flash 分别为 76% 和 84%。这证明模型选择确实影响成功率，但 Flash 的安全退出与两种模型各自出现的语义错误也再次证明：不能用单纯换模型代替证据清单、冷 Reviewer 和确定性门禁。

生产链第一次 25 条真实跑测又给出了更直接的边界：用户选择 Flash 时，系统内部把 Planner 静默切到 Pro，连续 7 条请求在 51～59 秒内未得到成功响应；撤掉换模后仍有结构化 Planner 请求耗尽阶段预算。进一步对照发现，架构实验对这类 JSON 任务显式关闭 thinking，而生产 Ledger 使用 `.low` 实际开启了 thinking；Fast 成功响应大多只需 0.6～2 秒。模型确实影响质量与延迟，但隐藏换模和不必要的推理开关都会制造日常 1K 文本失败。因此正式链路始终尊重用户当前模型，并对 Planner、Writer、Reviewer、Repair 的来源约束 JSON 任务关闭 thinking；“冷 Reviewer”只表示隔离调用和独立 Prompt，不再暗中改用另一模型。模型能力不足时由确定性门禁和显式失败兜底，而不是替用户做不可见的模型选择。

## 11. 历史生产候选记录（2026-08-18）

本节保留旧候选的代码、实验规模和结果，供追溯使用。以下路由、预算、Prompt 版本和测试数字均属于当时状态，不是当前三档候选的运行策略或验收结论；本轮实现与停止线以第 1～9 节为准。

用户于 2026-08-18 补充确认：日常长文本一般约 1,000 字，6K 并非常规输入。当时的生产候选让 80 字以下继续走一次 Fast 成稿与本地硬门禁，80～279 字仅在出现改口、上下文实体、显式结构等风险时升级 Ledger，280～1,800 字统一走 Ledger 主链；6K/8K 曾作为旧有界分片链路的压力边界。此处仅保留历史策略，不安排本轮超长测试。

当时生产候选的实现与测试记录：

1. `Evidence spans → typed Intent Ledger → structured Writer → cold Reviewer → targeted Repair → Confirm` 正式接入 `VoicePolishPipeline`；
2. 每个 Writer fragment 必须绑定交付 unit，确定性门禁检查来源事实、收件人、任务层、上下文映射、条件 cue、技术映射、文本完整度和仍未清理的高置信口述残片；
3. 单次运行共享 120 秒总预算，自动调用最多 6 次，Repair 只改 Reviewer 指向的 fragment；
4. Ledger 不读取原始安全上下文，只接收由本地 `EntityResolver` 证明的 canonical mapping；excluded/style/editor 内容不会反向强制写回正文；
5. 失败不再静默注入原文。Session 保留 canonical，并显示“重新润色 / 使用原转写”；只有用户明确选择后才走原转写出口；
6. Prompt v25 已把条件方向固化为本地 `operator_kind`（区分 `only_if` 与 `if_then`）。技术断词与口述符号不再信任 Planner 自报 mapping，而由本地从对应来源 span 机械推导；`Swift 6`、`Node 20` 等版本名不会被并写，路径与命令 canonical 也不能跨 span 扇出。普通数字允许中文与阿拉伯数字互换，但不得补原文没有的量词、单位或币种；
7. 质量 Runner 已把“预算调用尝试”与“成功 Provider 调用”分开记录：超时或本地失败仍计入尝试次数，但只有完成 HTTP 200 解析并落盘审计回执的请求才计入成功调用，避免把正常超时误报为审计链路丢失；
8. 约 1K 多约束文本的 Planner 与唯一一次 Planner Repair 使用 8,192 token 受控输出预算；初次瞬时网络失败与 schema repair 共用一个恢复槽，任何路径总尝试仍不超过 6 次，不切换用户选择的模型；
9. Reviewer 可用 `wrong_role` 明确阻断 Planner 将真实收件人正文误标为编辑指令、排除内容或删除项；这种错误只能进入有证据的局部修复或显式失败，不能因为每个 source span 都“形式上被引用”而假装润色成功；
10. 冻结候选 `bfa249a` 已完成 25/25 核心集，48 次成功 Provider 调用与 48 条外部回执一一对应；19 条生成合格成稿，6 条显式失败，没有把原文或不合格草稿伪装成润色成功。失败集中在技术 mapping 顺序、普通数字格式化、同段反向改口、AI Prompt 编辑指令和近 8K 压力样本的跨片旧值处置；
11. 针对这 6 条，Prompt v25 与本地证据层改为：忽略模型自报技术 mapping 并从来源机械推导；把无单位中文数字安全格式化为等值裸数字；只在同一 segment 有明确历史与取消证据时接受反向改口；把“先别开始研究，只整理任务”从 AI Prompt 收件人结构中移除；用明确对象“课程资料复核轮次不对”跨过无关的“最终决定”字样，精确作废三轮，同时保留其他仍有效的数字 3。该轮 46 项 Ledger、57 项 Core 与 3 项参考链，共 106 项定向回归全部通过；全量 Swift 测试 1,265 项通过、6 项条件跳过、0 失败。当时仍须完成全新签名候选与真实核心集复测后才能判断该轮是否收口。

该轮记录的停止线如下；本轮当前停止线见第 9 节：

1. 从冻结提交打包未安装签名候选；
2. 先跑不超过 1,000 字的无答案核心回归集，经正式 Swift 生产链路核对 Provider 回执、所选模型一致性、显式失败与逐条语义质量；
3. 核心集通过后再运行不超过 1,000 字的完整验收子集；
4. 最终由未参与实现的独立 Agent 复核冻结提交、候选、真实 Provider 输出和人工评分；
5. 独立 Agent 未明确通过时，L15 保持进行中，不安装候选，也不声称完成。
